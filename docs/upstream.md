## map iterator instances with one containing array or base pointer

Test files: `tests/5.1/target/test_target_map_iterators.c`, `tests/5.1/target/test_target_map_iterators.F90`, `tests/5.2/declare_mapper/test_declare_mapper_iterator.c`.

tests/5.2/declare_mapper/test_declare_mapper_iterator.c line 26: `map(iterator(it = 0:v.len), tofrom: v.data[it])` instantiates the list items v.data[0], ..., v.data[v.len-1], which all have the base pointer v.data. OpenMP 5.1 §2.21.7.1 p.353 (also 5.2 §5.8.3 p.156, 6.0 §7.9.6 p.286): "If an expression that is used to form a list item in a map clause contains an iterator identifier, the list item instances that would result from different values of the iterator must not have the same containing array and must not have base pointers that share original storage." Filed as OpenMP_VV#921. Suggested fix: an iterator whose instances are sections of distinct storage (an array of pointers, map(iterator(it = 0:M), tofrom: p[it][0:N])), or a single-value iterator. The same defect in tests/5.1/target/test_target_map_iterators.{c,F90} (all instances in the containing array test_lst) was fixed upstream (issue #868, PR #869: test_lst[it][:1] over an array of pointers); the fixed Fortran test passes on CCE 19/20/21 on both GPUs (rerun), the fixed C test is still rejected by AFAR amdclang and CCE craycc at the default OpenMP 5.1 ("incorrect map type modifier", the front-end defect clang-c-map-iterator-omp51.c). Observed: every compiler fails the declare_mapper_iterator test at link time ("undefined symbol: it").

Compilers where the tests fail here: afar. Flags: flag:c:52:omp.clause.map.iterator:afar:headline:ours_ok_suite_fails, flag:c:60:omp.clause.map.iterator:afar:headline:ours_ok_suite_fails

## omp_target_is_accessible returning false fails the test

Test files: `tests/5.1/target/test_target_is_accessible.c`, `tests/5.1/target/test_target_is_accessible.F90`.

tests/5.1/target/test_target_is_accessible.c and .F90 (as changed by OpenMP_VV #891) treat a false result of omp_target_is_accessible as a failure. The routine "returns true if the storage of size bytes starting at the address given by ptr is accessible from device device_num. Otherwise, it returns false" (OpenMP 5.1 §3.8.4 p.417; 5.2 §18.8.4 p.390; 6.0 §25.2.2 pp.605-606: non-zero / zero), so false is the conforming answer for malloc'ed (C) or allocated (Fortran) host memory on a device without unified shared memory. C: when the routine returns false, check_device() returns OMPVV_SKIPPED_EXIT_CODE, but main() does `OMPVV_TEST_AND_SET_VERBOSE(errors, check_device() != 0)`, so the skip becomes errors = 1 and the test reports "Test failed" and exits 1 instead of skipping. Fortran: the ELSE branch does `OMPVV_TEST_AND_SET(errors, check_test.EQ.0)` ("This test will be skipped with error = 1"), a failure by construction. Suggested fix: propagate the skip (C: `int r = check_device(); if (r == OMPVV_SKIPPED_EXIT_CODE) OMPVV_REPORT_AND_RETURN(r);`; Fortran: no error when the routine returns false, or a skip status), or require unified_shared_memory as test_target_is_accessible_with_usm.c does. Observed: on a discrete MI250X (gfx90a) and on the MI300A at HSA_XNACK=0, AFAR and CCE 20/21 return false and the test fails with "omp_target_is_accessible returned false"; at HSA_XNACK=1 (MI300A) they return true and the test passes.

Compilers where the tests fail here: afar_g90, cce20_g90, cce21_g90. Flags: flag:c:52:omp.clause.firstprivate:afar_g90:gfx90a:ours_ok_suite_fails, flag:c:52:omp.clause.firstprivate:cce20_g90:gfx90a:ours_ok_suite_fails, flag:c:52:omp.clause.firstprivate:cce21_g90:gfx90a:ours_ok_suite_fails, flag:c:60:omp.clause.firstprivate:afar_g90:gfx90a:ours_ok_suite_fails, flag:c:60:omp.clause.firstprivate:cce20_g90:gfx90a:ours_ok_suite_fails, flag:c:60:omp.clause.firstprivate:cce21_g90:gfx90a:ours_ok_suite_fails, flag:f90:52:omp.clause.firstprivate:afar_g90:gfx90a:ours_ok_suite_fails, flag:f90:52:omp.clause.firstprivate:cce20_g90:gfx90a:ours_ok_suite_fails, flag:f90:52:omp.clause.firstprivate:cce21_g90:gfx90a:ours_ok_suite_fails, flag:f90:60:omp.clause.firstprivate:afar_g90:gfx90a:ours_ok_suite_fails, flag:f90:60:omp.clause.firstprivate:cce20_g90:gfx90a:ours_ok_suite_fails, flag:f90:60:omp.clause.firstprivate:cce21_g90:gfx90a:ours_ok_suite_fails

## the C header returns the error count as the exit status

Test files: `ompvv/ompvv.h`.

Observed here (rerun, OpenMP_VV f7d95b34): 42 runs of the headline toolchains (and 9 of the cce21_4 regression runs) exit 0 but print "Test failed" (the error count is a multiple of 256), in five C tests: tests/4.5/target_teams_distribute_parallel_for/test_target_teams_distribute_parallel_for_devices.c, tests/4.5/target_teams_distribute_parallel_for/test_target_teams_distribute_parallel_for_schedule_private.c, tests/5.0/target_update/test_target_update_mapper_from_discontiguous.c, tests/5.0/target_update/test_target_update_mapper_to_discontiguous.c (every CCE cell; AFAR at HSA_XNACK=1 for three of them) and tests/5.0/loop/test_loop_bind_device.c (CCE 20 on gfx90a, CCE 21 at HSA_XNACK=0 and on gfx90a). The suite's own Makefile (CHECK_OUTPUT) reads the exit status, so it would record them as PASS; our baseline reads the result line (offload.engine.baseline.suite_result).
