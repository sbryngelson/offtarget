Portable: correct with unified memory, separate memory and a discrete GPU

Every program ran on the MI300A at XNACK 1 (unified memory) and at XNACK 0 (copy mode: separate host and device memory, as on a discrete GPU), and on Tioga's MI250X (gfx90a, a discrete GPU with its own memory, XNACK 0 only). A feature is portable on a compiler when it is correct in all three. For NVHPC (A100, 25.11 and 26.9) portable means correct in separate and in managed memory; managed not verifiable means a copy-mode check of data managed memory shares. MI300A only means correct in both MI300A modes and failed on gfx90a; gfx90a not verifiable means the gfx90a run gives no verdict. XNACK 1 only means correct with unified memory but not in copy mode, where a mapping error shows. Failed in both means an observed failure (rejected, wrong answer, crash) in both modes; failed at XNACK 0, XNACK 1 unverified means the copy-mode run failed and the XNACK 1 run cannot tell (nothing observable, or a check that runs only in copy mode); requirement refused is a conforming refusal of a requires directive; not verifiable means neither mode gives an observable verdict (no oracle, unobservable, ignored). Random-program testing (Fortran OpenMP: AFAR, CCE and NVHPC)

Coverage: Fortran only (there is no C generator yet). Campaigns c1, b0 to b5, the x0 campaigns, s1 and s1x0 use the OpenMP 5.2 spellings and ran on AFAR and Cray CCE 19, 20 and 21 on the MI300A; NVHPC rejected almost all of their programs (193 of a 200-program sample) for the 5.2 syntax alone. Campaigns n0x0 and n1x0 use generator fuzz-4s50: the same programs with the OpenMP 5.0/5.1 spellings NVHPC accepts (declare target to, defaultmap without the all category, order(concurrent); the same model, still legal OpenMP 5.2), 1000 seeds each (n0x0 without base-language groups, n1x0 with all five), run on AFAR and CCE at HSA_XNACK=0 and on NVHPC 25.11 and 26.9 in separate memory on the A100; NVHPC compiled about 20% of the n0x0 programs (the rest use features it lacks: masked, task_reduction, nontemporal, thread_limit on target) and 8% of n1x0 (most rejections there are base-language features: an intrinsic in an initialization expression, declare reduction or declare mapper). Use the campaign menu to switch. Seeded random offload programs, each checked against a Python model and run on those compilers at XNACK 1 (the x0 campaigns, s1x0, n0x0 and n1x0 at XNACK 0). Agree means the compiler gave the model's answer. Every program passed the legality checks, so compile rejected means a compiler refused a legal program, crash means an internal compiler error, and wrong code means the run finished with another answer. The first campaign (c1, 2400 programs) varies only the OpenMP constructs and clauses. Campaigns b1 to b5 (300 programs each) add one group of base-language features per stage, and b0 is the control: the same seeds without a group. Campaign s1 (10000 programs) combines all five groups, and s1x0 runs its first 2500 seeds at XNACK 0 (copy mode). A program that fails on the host with every compiler is noncompliant and is counted nowhere. How to read this

  • Rejected counts the compiler refusing the feature. Rejection not counted means the compiler refused something else in the program, such as declare simd or uses_allocators, so the feature itself was not tested.
  • Accepted, not checkable means the program compiled and ran, but a single run cannot tell the feature from its absence. That covers clauses equal to a default and clauses with no observable effect.
  • Wrong answer, oracle unaudited covers schedule, ordered and bind(thread). The check could not be validated against a mutant, so treat those as measurements.
  • "Only where compilers differ" keeps rows whose headline results (XNACK 1 on the MI300A, separate memory on the A100) are not all the same, which is the quickest way to see where a compiler or a version changed something.
  • XNACK 1 is unified memory (the MI300A default here); XNACK 0 is copy mode, where host and device memory are separate as on a discrete GPU. At XNACK 1 a missing or wrong map often still gives the right answer, so Portable on lists the compilers that are correct in both modes: that is the result to rely on for portable code. Every program ran in both modes (the XNACK 0 runs on other nodes than most XNACK 1 runs).
  • NVHPC (NVIDIA HPC SDK 25.11 and 26.9, nvfortran and nvc) ran every OpenMP and OpenACC program and every omp_vv test on an NVIDIA A100 (wingtip) in separate memory (-gpu=mem:separate, the headline: host and device memory apart, so a missing map shows) and in managed memory (-gpu=mem:managed). Its portable verdict asks for both modes; it has no XNACK or gfx90a column. NVHPC rejects more programs at compile time than the AMD compilers, most of all at OpenMP 6.0.
  • widened (a chip next to the id, and the Catalog filter) marks programs added by the widened catalog: base-language features in device code (derived types, allocatables, character, block, ...), directives outside the spec slice, and pairs of features combined in one program. They are OpenMP 5.2 (Fortran and C) or OpenACC 3.4 (Fortran). The other rows are the spec slice, one feature of the OpenMP or OpenACC specification per program.
  • gfx90a is the same compiler on Tioga's AMD Instinct MI250X, a discrete GPU with its own memory, at XNACK 0 only (XNACK is not recommended there). Portable on needs it correct too. Every cell agreed with the MI300A XNACK 0 cell except one intermittent AFAR failure.
  • Illegal-variant programs, vendor claims and the findings (compiler bugs with reproducers) are in the full report and are not drawn here.
  • Expected (OpenMP table) says how far the program's expected result is backed by independent sources, for the programs where a compiler's result disagreed with the claim. Trusted: two independent sources agree. Provisional: not enough evidence. Disputed: the sources disagree. Empty: no check was needed, or the program is a C 5.2/6.0 port (the expected-result check covers Fortran and, since The C 5.0 slice: the program's own oracle and sequential elision by gcc and amdclang).
  • C and Fortran programs of the same feature are separate rows (C ids contain -c-). The C slice covers 5.0, 5.2 and 6.0 (5.0 since The ports of the 5.0 Fortran programs, with C 5.0's forms, e.g. default(shared | none) only).
  • All entries are provisional: the restriction rules and clause grammar are still waiting for owner review.
